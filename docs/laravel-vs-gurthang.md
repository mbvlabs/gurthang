# Laravel vs Gurthang: Feature Comparison

A feature-by-feature comparison of Laravel (PHP) against Gurthang, the
Linux-only "project pad" for Rails-shaped Rust web apps (Axum + SQLx + Inertia
React + a Postgres job queue). The goal is to gauge how far Gurthang has come
toward "Laravel in Rust" and where it should lean into being *agent-optimized*
rather than a literal port.

> Legend: **Full** = first-class equivalent, **Partial** = exists but narrower or
> different shape, **Absent** = no equivalent today, **Diverges** = solved a
> different way on purpose.

---

## 0. Executive summary

Gurthang reproduces Laravel's *developer workflow* more than its *object model*:

- The **Artisan-style CLI** is the closest match: `new`, `generate *`, `db *`,
  `routes`, `run`, `build`, `tools` map almost 1:1 onto `laravel new`, `make:*`,
  `db:*`, `route:list`, `serve`, and `optimize`.
- **Routing, controllers, middleware, sessions, CSRF, queues, mail, and config**
  all have real equivalents with a similar mental model.
- The **Eloquent layer is deliberately replaced** by schema-first SQLx: there is
  no ORM, no relationships, no dynamic attributes. Models are plain structs with
  compile-checked SQL.
- The **view layer is Inertia React, not Blade**, and page props are a
  Rust-sourced, `ts-rs`-exported contract rather than Blade templates.
- Large Laravel surfaces have **no equivalent yet**: authorization (Gates /
  Policies), events & listeners, broadcasting, notifications, caching,
  scheduler/cron, file storage, localization, rate limiting, pagination,
  testing helpers, search (Scout), API tokens (Sanctum/Passport), and the
  service container / facades.

The interesting angle: several Gurthang design choices are *already* better for
AI agents than Laravel's equivalents (deterministic schema-first generation,
typed end-to-end contracts, `sync --check` drift detection, compile-checked
SQL). The report closes with concrete opportunities to push further.

| `php artisan db:seed [--class]` | `gurthang db seed [name] [--list]` | Partial |
| `php artisan make:model` | `gurthang generate model <Name>` | Full (schema-first) |
| `php artisan make:migration` | `gurthang generate migration <name>` | Partial |

| `php artisan make:job` | `gurthang generate job <Name>` | Full |
| `php artisan make:mail` | `gurthang generate mailer <Name>` | Full |
| `php artisan make:command` | `gurthang generate task <Name>` | Full |
| `php artisan queue:work` | `gurthang` app run in `worker` mode | Full |
| `php artisan optimize` / `npm run build` | `gurthang build` | Full |
| `php artisan tinker` | none (no REPL) | Absent |
| `php artisan test` | `cargo test --workspace` | Diverges |
| `php artisan config:cache` etc. | none (compiled binary; no cache warmup) | Diverges |
| `php artisan schedule:run` | none | Absent |
| `php artisan make:request / policy / middleware / seeder / event / listener / observer / notification / rule / test / provider` | none | Absent |
| `php artisan make:model -m` (model + migration together) | `generate model` + `generate migration` separately | Partial |
| Laravel Sail (Docker) | none (native Linux + `mold`) | Diverges |

Gurthang also has **commands Laravel does not**: `gurthang sync model|routes|payloads|factory|factories [--check]`
(regenerate artifacts from the live schema and detect drift) and
`gurthang tools [check|sync]` (verify/install the toolchain: `clang`, `mold`,
`sqlx-cli`, Node, `psql`). `gurthang middleware` prints the YAML middleware
stack with enable flags.

**Notes**
- Gurthang generation is **non-interactive and deterministic**; the only prompt
  is the destructive-DB `yes` confirmation, bypassable with `--force`.
- Codegen is split into `generate` (create from a name or the DB) vs `sync`
  (regenerate from the live schema), with `--check` for CI. Laravel has no
  first-class "regenerate + diff" concept.

## 2. Routing

| Laravel | Gurthang | Status |
|---|---|---|
| `routes/web.php`, `routes/api.php` | `src/routes/*.rs` route-constant catalog | Full |
| Named routes (`->name('x')`, `route('x')`) | `Route { name, path }` consts; `.url()`, `.url_with(id)` | Full |
| `Route::get/post/put/patch/delete` | `mount!` + axum verb fns | Full |
| Route parameters (`{id}`) | `{id}` in `Route::path`, `.url_with(id)` | Full |
| Route groups / prefixes / middleware groups | router `merge` + `MiddlewareLayer` stack | Partial |
| Resource routes (`Route::resource`) | `gurthang generate scaffold` emits the 7 REST routes | Partial (generate-time) |
| Route model binding | none (controllers `find` by id) | Absent |
| Route caching (`route:cache`) | none needed (compiled) | Diverges |
| `Route::fallback` | `fallback` middleware (embedded 404 page) | Full |
| Rate limiting (`throttle`) | none built in | Absent |

Gurthang binds a controller *instance method* to a route via `on(ctrl, Method)`
and the `mount!` macro, which expands to `axum::Router::route(...)`:

```rust
mount!(auth, {
    crate::routes::auth::REGISTER => get(auth, Auth::new_register),
    crate::routes::auth::REGISTER_CREATE => post(auth, Auth::register_user),
});
```

The route catalog is also exported to the frontend: `gurthang sync routes`
writes `resources/js/routes.ts` with a `path(name, params)` helper (Laravel's
Ziggy equivalent), so Rust remains the single source of truth for URLs.

## 3. Controllers, Middleware, DI

| Laravel | Gurthang | Status |
|---|---|---|
| Controllers in `app/Http/Controllers` | `src/controllers/*.rs` (Clone struct + methods) | Full |
| Resource / invokable controllers | generated controllers with named actions | Full |
| Dependency injection (container) | axum `State<Context>` + `FromRef` extraction | Diverges |
| Route middleware / groups | `MiddlewareLayer` trait-object stack from YAML | Full |
| Middleware aliases & parameters | named layers, reorder via `MiddlewareStackExt` | Full |
| `HandleCors`, `ThrottleRequests`, `VerifyCsrfToken`, `StartSession`, `Authenticate`, `SubstituteBindings` | `cors`, `csrf`, `session_auth`, `secure_headers`, `remote_ip`, etc. | Partial |
| Service container / service providers | `Hooks` lifecycle + `Initializer` trait | Partial |
| Facades | none (explicit `Context` fields) | Diverges |

Gurthang ships a **default 15-layer middleware stack** configured in
`config/<env>.yaml` and introspectable via `gurthang middleware`:
`limit_payload, cors, catch_panic, etag, remote_ip, compression,
timeout_request, static, secure_headers, logger, request_id, fallback,
powered_by, csrf, session_auth`. Apps can `insert_before`, `insert_after`,
`replace`, or `delete` layers by name. There is no user-land `make:middleware`
generator yet.

Boot lifecycle (`Hooks`): `boot → initializers → before_run → before_routes →
routes → middlewares → after_routes → initializer.after_routes → serve →
on_shutdown`. This is the closest analog to Laravel service providers.

## 4. Models / ORM / Database

| Laravel | Gurthang | Status |
|---|---|---|
| Eloquent models | plain structs in a separate `models` crate | Diverges |
| Relationships (`hasMany`, `belongsTo`, …) | none (explicit SQL joins) | Absent |
| Query builder | SQLx `query!` / `query_as!` | Diverges |
| Accessors / mutators / casts | explicit typed fields + `From<Form>` impls | Diverges |
| Scopes | plain `impl` methods (`find`, `list`, …) | Partial |
| Soft deletes | none generated | Absent |
| Model observers | none | Absent |
| Factories | generated typed builder factories | Full |
| Seeders | `src/bin/seed.rs` + `db seed` | Partial |
| Mass assignment protection | explicit `Create`/`Update` data structs | Diverges |
| Pagination | none built in | Absent |
| Collections / helpers (`Str`, `Arr`) | Rust std / `heck` / `uuid` | Diverges |
| Multiple DB engines | PostgreSQL only | Diverges (intentional) |

Gurthang is **schema-first**: `gurthang generate model Widget` introspects the
live Postgres database (via `information_schema`) and emits a typed struct, a
`CreateWidgetData` / `UpdateWidgetData`, CRUD methods using compile-checked
`sqlx::query_as!`, a wrapper module, and a factory. There is no ORM; "models
never own SQL" only in the sense that controllers never do — the `models` crate
does, and it is isolated so a controller edit does not recompile SQL macros.

**Agent-relevant**: SQL is validated at compile time against `.sqlx` offline
metadata, so an agent's query mistakes surface as compiler errors, not runtime
500s. Laravel's Eloquent cannot offer this.

## 5. Migrations & schema

| Laravel | Gurthang | Status |
|---|---|---|
| `database/migrations` | `migrations/NNNN_slug.sql` | Full |
| Schema builder (`Schema::create`) | raw SQL migration files | Diverges |
| `up()` / `down()` + rollback | forward-only SQL; no `down` | Partial |
| `migrate:rollback` / `:reset` / `:refresh` / `:fresh` | `db rebuild` (drop+create+migrate) | Partial |
| Migration squashing | none | Absent |
| Schema introspection | `generate model` reads live schema | Full (inverted) |

Migrations are plain `.sql` files applied by the SQLx migrator; `db migrate up`
also runs `cargo sqlx prepare`. Gurthang does **not** parse migrations to
generate models — it reads the live database, so you migrate first, then
generate.

## 6. Validation

| Laravel | Gurthang | Status |
|---|---|---|
| FormRequest classes | none generated | Absent |
| `$request->validate([...])` rules | hand-rolled `validate` in `models`/services | Partial |
| Validation error bag → redirect back | `errors` in Inertia shared props | Full |
| `old()` input repopulation | `old.email` stored in session | Partial |
| Custom rules / rule objects | none | Absent |
| `make:request` | none | Absent |

Validation follows the **Inertia redirect model**: on failure the controller
stores `errors` (and `old.*`) in the session, redirects back (`303`), and the
`errors` bag is shared to the page. There is no validation rule DSL or
FormRequest equivalent yet.

The generated app ships a working auth vertical slice: `controllers/auth.rs` +
`services/auth.rs` (`AuthBackend`), `models/src/user.rs` (Argon2 hashing,
email normalization, unique-violation → `DuplicateEmail`), a timing-equalizing
dummy-hash on unknown users, and a protected `/dashboard`. Registration also
enqueues a welcome email.

## 9. Sessions, CSRF, cookies

| Laravel | Gurthang | Status |
|---|---|---|
| Session drivers (file/db/redis/…) | Postgres store only | Partial |
| `sessions` table | `tower_sessions (id, data, expiry_date)` | Full |
| Inactivity expiry | 7 days (`Expiry::OnInactivity`) | Full |
| HttpOnly / SameSite / Secure flags | configurable (`config.session`) | Full |
| CSRF `VerifyCsrfToken` | `csrf` middleware (double-submit cookie) | Full |
| `@csrf` / `X-XSRF-TOKEN` | `XSRF-TOKEN` cookie ↔ `x-xsrf-token` header | Full |
| Flash data | `flash.*` in session, shared to page | Full |
| Signed URLs | none | Absent |
| Cookie encryption | none (sessions serialized with MessagePack) | Partial |

CSRF is deliberately ordered *outside* `session_auth`, and the token is a random
UUID double-submitted as a JS-readable cookie (the Inertia XSRF convention).

## 11. Views & frontend

| Laravel | Gurthang | Status |
|---|---|---|
| Blade templates | Inertia React pages (`.tsx`) | Diverges |
| Blade components / layouts / slots | React components | Diverges |
| Inertia (first-party) | first-party `gurthang-inertia` adapter | Full |
| Livewire | none | Absent |
| Vite + HMR | Vite 7 dev server + React Fast Refresh | Full |
| Tailwind | Tailwind v4 via `@tailwindcss/vite` | Full |
| SSR | optional Node/Bun SSR, embedded bundle, graceful CSR fallback | Full |
| Page props as source of truth | Rust `InertiaPage`/props + `ts-rs` export | Full (stronger) |
| `@vite` directive / manifest | `AssetResolver` (dev server vs `manifest.json`) | Full |

Gurthang has **no Blade/Tera** (the README explicitly drops Tera and the
Tailwind standalone CLI). The view layer is Inertia React, and page contracts
are Rust structs deriving `Serialize + TS` and exported to
`resources/js/generated/*.ts`. The SSR bundle is embedded in the binary
(`include_bytes!`) and runs a supervised Node ≥ 22 worker with a
`gurthang:ssr:` line protocol, falling back to client rendering on failure.

## 12. Queues & jobs

| Laravel | Gurthang | Status |
|---|---|---|
| Queue drivers (database/redis/sqs) | Postgres-backed queue (app-owned) | Partial |
| `jobs` / `failed_jobs` tables | `background_jobs` table | Full |
| `dispatch()` / `ShouldQueue` | `JobQueue::enqueue` / `PerformJob` | Full |
| Delayed jobs (`->delay`) | `enqueue_at` / `enqueue_in` | Full |
| Job retries / `tries` / `maxAttempts` | `max_attempts` + exponential backoff | Full |
| `release()` / backoff | lease expiry re-claim + retry delay | Full |
| `queue:work` worker loop | `JobWorker` run loop | Full |
| Batches / chains | none | Absent |
| Horizon (dashboard) | none | Absent |
| Job middleware / rate limiting | none | Absent |
| `php artisan queue:failed` | query `background_jobs` (status='failed') | Partial |
| Transactional dispatch (`afterCommit`) | `enqueue_in(&mut PgConnection, …)` | Full |

The queue is atomic via `FOR UPDATE SKIP LOCKED`, uses expiring leases
(visibility-timeout), `LISTEN`/`NOTIFY` wake-ups with polling fallback, and
bounded retries. `WorkerConfig` (concurrency, poll interval, lease, timeout)
comes from YAML or `JOB_*` env vars. Dispatch on an existing connection makes
the business change and its job commit atomically.

## 17. Where Gurthang is *already* agent-optimized

These are properties Laravel does not have, and they matter for AI-driven
development:

1. **Compile-checked SQL.** `sqlx::query!` / `query_as!` with offline `.sqlx`
   metadata means a wrong column or type is a build error. An agent iterates
   against the compiler, not against production.
2. **Schema-first generation.** `generate model`/`scaffold` read the live
   database, so the agent writes a migration, applies it, and generates
   accurate code — no guessing field names or types.
3. **Typed, end-to-end contracts.** Rust route consts → `resources/js/routes.ts`
   (Ziggy-like) and Rust `Props` → `ts-rs` `.ts` files. The agent edits Rust and
   the frontend contract follows.
4. **`sync … --check` drift detection.** `sync model|routes|payloads|factory|
   factories --check` fails when generated artifacts are stale — perfect for an
   agent's verify step and for CI.
5. **Non-destructive by default.** Generators refuse to overwrite existing
   files (`region::write_if_allowed`); `sync` is the explicit overwrite path.
   Agents cannot silently clobber hand-edited code.
6. **Deterministic wiring.** Generators patch `src/app.rs` (`add_route`,
   `tasks.register`, `connect_workers`) with exact, idempotent insertions.
7. **Scriptable, non-interactive CLI.** Only destructive DB ops prompt, and
   `--force` bypasses. Exit codes and stdout are stable and parseable.
8. **Single-command dev loop.** `gurthang run` supervises Vite + backend with
   debounced restart, so an agent can start the whole stack with one call.
9. **Structured, greppable stack.** `gurthang middleware` and `gurthang routes`
   print the effective configuration, so an agent can introspect state instead
   of reading source.
10. **`gurthang tools`.** Explicit toolchain check/install removes a whole class
    of "works on my machine" failures for autonomous setup.

## 18. Opportunities to optimize further for agents

Concrete, high-leverage additions, ordered roughly by value:

1. **Machine-readable output.** Add `--json` to `routes`, `middleware`,
   `db migrate status`, and every `sync --check` so agents parse structured data
   instead of screenshots of aligned text.
2. **A `gurthang check` aggregate.** One command that runs `sync * --check`,
   `cargo check`, `cargo sqlx prepare --check`, and `tsc --noEmit`, returning a
   single pass/fail with a unified diff of drift. This is the agent's "is the
   repo consistent?" button.
3. **`generate` dry-run as a plan.** Every generator already supports
   `--dry-run`; emit it as a diff/manifest (not just a list) so an agent can
   review a change before applying it.
4. **Authorization primitives.** Gates/policies are the biggest missing
   Laravel feature and a common agent task; a small `Policy`/`Ability` trait
   plus `generate policy <Name>` would close it cheaply.
5. **Validation rules.** A typed `Validator`/`Rule` set and `generate request`
   would replace hand-rolled checks and give agents a stable target.
6. **Pagination + collections.** A `Page<T>`/paginate helper and a few
   collection conveniences would remove repetitive code agents otherwise invent.
7. **A cache trait with a Postgres-backed default.** Laravel's `Cache::remember`
   is ubiquitous; a tiny trait keeps agents from re-implementing caching.
8. **Events/listeners (typed).** A minimal in-process event bus with typed
   listeners would cover observers/notifications without a full framework.
9. **`generate middleware` / `generate provider`.** Round out the generator
   surface so every extension point has a scaffold.
10. **Observability hooks.** `tracing` spans per job/request plus a
    `gurthang jobs` inspector (queued/running/failed counts) would let agents
    observe and debug async work.
11. **A test scaffold (`generate test`).** Even a minimal HTTP + model test
    template would give agents a starting point and a runnable assertion.
12. **Docs as a queryable resource.** Emit a `gurthang manifest` describing
    every command, flag, and generated file so agents can self-discover the
    framework instead of relying on this report.

## 20. Bottom line

Gurthang is best understood not as "Laravel in Rust" but as **"Laravel's
workflow, rebuilt on a compiler-checked, schema-first, agent-first substrate."**
It nails the daily loop (new → migrate → generate → run → build) and the
request/routing/queue/mail/config surfaces, deliberately discards Eloquent and
Blade, and has not yet built the "batteries" Laravel is famous for (authz,
events, notifications, cache, scheduler, storage, localization, pagination).

For the agentic goal, the winning strategy is *not* to clone every Laravel
class. It is to double down on what Laravel cannot offer an autonomous
developer: deterministic generation, typed contracts, drift detection, and
machine-readable introspection — while selectively adding the few Laravel
conveniences (authorization, validation, pagination, cache) that agents reach
for most often.
